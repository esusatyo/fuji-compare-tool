## Context

`specSources[]`, `priceSource`, `imageSource`, and `imageCredit` citation objects exist in the schema and are partially populated per-brand (see proposal). `productUrl` is populated on all 810 camera/lens entries. Nothing renders any of this today. The rendering surface is split across two independently-maintained code paths that must stay in sync:

- **Interactive pages** (`engine.js`'s `renderTable()`) — brand pages and the cross-brand `compare/` page, 2–4 user-adjustable slots, re-rendered on every slot change.
- **Static vs-pages** (`scripts/generate-seo.js`) — prerendered same-brand and cross-brand HTML, 2 fixed columns, regenerated by a build script that cannot `<script src>` or `require()` `engine.js` (it's a browser-only IIFE-registration file per this repo's brand-isolation invariant).

The user has already settled the visual/UX questions in review: reference rows live inside the existing spec table/vs-card (not a separate card), row labels are **Spec source / Price source / Image source / Product page**, `productUrl` is the fallback, and the section stays expanded with CSS truncation (not collapse) for long URLs.

## Goals / Non-Goals

**Goals:**
- One shared row/labeling/fallback/dedup algorithm, expressed twice (engine + generator) because the two runtimes can't share code, but verified identical via a test comparing their output on the same sample items.
- Every item shows at least one reference today (via `productUrl` fallback), even brands with zero `specSources` coverage (Panasonic, Sigma).
- No visual regression to existing spec-table/vs-card behavior (collapse toggle on other sections, winner highlighting, mobile slot hiding, brand-conditional "—" cells) — References is additive.
- Struggling/missing titles degrade to a readable label, not a raw 80-character URL.

**Non-Goals:**
- Backfilling `title` (or any citation) onto existing items — left to the next refresh/price-check sweep, per this change's proposal.
- Fixing dead links `test:links` surfaces — reported only, per user decision this session.
- Per-field inline citations (a citation icon next to each spec value) — rejected earlier in favor of one block per item, which is simpler and matches how `imageCreditsBlock()` already presents citations site-wide.
- Winner highlighting on reference rows — these aren't comparable numeric/boolean specs.

## Decisions

### 1. Row set is fixed at four, not dynamic per available source
**Decision:** Always render all four rows (Spec source, Price source, Image source, Product page), with "—" for a brand/item with nothing in that row.
**Why:** Matches how every other spec row already works (winner-less rows still render, e.g. text specs), keeps the row count identical across all four compare-page columns so the grid doesn't jump, and makes the empty state self-explanatory instead of a collapsing table.
**Alternative considered:** Omit rows with zero data for the whole visible set. Rejected — with 2–4 slots mixing brands (compare page), "this row doesn't exist because none of these 4 happen to have image sources" is a worse experience than one visible "—".

### 2. `productUrl` is both its own row AND the universal fallback, with dedup against it
**Decision:** Product page always shows `productUrl` (skipping generic `/cameras/` index URLs, matching existing `renderSlot()`/`productCardHTML()` logic at `engine.js:886` / `generate-seo.js:424`). If a `specSources[]` entry's URL equals `productUrl`, it's suppressed from the Spec source row (shown only once, in Product page) to avoid the same link appearing twice in one item's column.
**Why:** Today, a T1 spec source is very often literally the same product page already linked as `productUrl` (see fujifilm/data.js:116, citing the same `fujifilm-x.com/global/products/cameras/x-e4/` page). Showing it twice looks like a bug, not a feature.
**Alternative considered:** No dedup, just show both. Rejected as visually redundant for the majority of currently-populated Fujifilm/Nikon entries.

### 3. Citation `title` is optional; renderer falls back to hostname
**Decision:** `checkCitation()` in `tests/helpers/schema.js` accepts an optional non-empty-string `title`. The collector emits `title` when present, else a generated label: hostname with `www.` stripped (e.g. `adorama.com`) for T2/T3/T4/NEWS, or `"<Brand-facing product page>"` copy is NOT auto-generated for T1 — hostname is used uniformly for all tiers to keep the collector tier-agnostic and avoid hand-maintaining a per-tier label format that would need updating as new source domains appear.
**Why:** The user asked for the structure now, real titles in the next sweep. A hostname fallback means the page is useful and honest immediately (a real URL you can inspect) without inventing text no one wrote.
**Alternative considered:** Require `title` before a citation renders (hide untitled ones). Rejected — it would hide the majority of current citations (0 of the ~171 existing `priceSource`/`specSources` entries have a `title` field), defeating the point of shipping the structure now.

### 4. One collector, two implementations, one parity test
**Decision:** `collectReferences(item)` is implemented once in `engine.js` (ES2020+, browser globals) and once in `scripts/generate-seo.js` (Node, CommonJS-style top-level functions matching that file's existing style). A new logic-tier test loads both, runs each against the same handful of real items pulled from live brand data, and asserts identical `{kind, text, url}` output.
**Why:** `engine.js` cannot be `require()`'d by the Node generator (browser-only IIFE globals, no module.exports, and the repo's CLAUDE.md explicitly forbids introducing shared imports between engine and data files) — this is an existing, deliberate constraint, not something this change should work around. Duplication is the cost; the parity test is what keeps it safe, the same pattern already implicitly relied on for the (smaller) `productUrl`-cleanup logic that's independently duplicated at `engine.js:886` and `generate-seo.js:424` today.
**Alternative considered:** Extract a shared plain-JS module loaded by both via different mechanisms (`<script>` tag in browser, `require()` in Node). Rejected as larger surface area than this change needs — `engine.js` truly is not `require()`-able as-is (it assumes `window`/`document`), and building a dual-load shim is disproportionate to ~25 lines of logic.

### 5. Interactive-page References section reuses `spec-section` markup but is not collapsible
**Decision:** Same `<div class="spec-section">` / `.section-header` / `.section-body` wrapper as every other section, so it inherits layout, spacing, and the mobile 2/3/4-slot grid for free — but the header renders without the `.section-toggle` arrow and without a click listener, and `.section-body` never gets `.collapsed` added.
**Why:** Cheapest way to get correct grid/spacing behavior "for free" (verified against the existing 692 passing render tests as a baseline). The user explicitly asked for always-expanded, not collapsed-by-default.
**Alternative considered:** A bespoke non-section markup block after the table. Rejected — would need to reimplement responsive column widths that `spec-section`/`spec-row` already solve.

### 6. Truncation is CSS-only; no JS string-shortening
**Decision:** `.ref-link { display:block; overflow:hidden; text-overflow:ellipsis; white-space:nowrap; min-width:0 }` with the full URL in the anchor's `title=` attribute. Multiple sources in one cell stack as multiple `.ref-link` block elements.
**Why:** Keeps the link's `href` (and thus click behavior/analytics) untouched — only the rendered text is visually clipped. `min-width:0` is required because the cell is a grid/flex child (existing `.spec-value` sizing) that would otherwise refuse to shrink below its content's natural width.
**Alternative considered:** JS-side `text.slice(0, N) + '…'`. Rejected — loses information at different viewport widths where more/less room is available; CSS ellipsis adapts automatically.

## Risks / Trade-offs

- **[Duplication drift between engine.js and generate-seo.js collectors]** → Mitigated by the parity test (Decision 4); any future change to one without the other fails CI.
- **[`test:links` may newly fail on pre-existing dead source URLs once those URLs become checked]** → Out of scope per user decision; failures are listed in the PR description as follow-up leads (matching the existing pattern in `image-refresh-run-sep-2026` memory), not blocking this PR's merge as long as the *rendering* tests are green. If `test:links` itself would go red project-wide, it's run with `RUN_LINK_TESTS=1` separately and reported, not treated as a gate for this change.
- **[Untitled citations show a bare hostname, which is less useful than a real title]** → Accepted; matches the user's explicit "structure now, content in the next sweep" framing. Once `title` starts getting backfilled, pages improve automatically with no further code change.
- **[Adding a fourth reference type — Product page — to items that previously had zero visible citations changes the vs-page's apparent "sourced-ness"]** → Acceptable: `productUrl` is always a real, working product page already used elsewhere on the same page (View Product link), so this isn't fabricating a source, just surfacing one that already existed.

## Migration Plan

1. Schema change (`title` field) — additive, no migration needed for existing data.
2. Engine + CSS changes — additive rendering, ship behind no flag (small, low-risk, covered by tests).
3. Generator changes — regenerate all vs-pages in the same PR so generated HTML never drifts from the generator source (existing repo convention).
4. Skill doc updates — informational only, affects future sweeps, not this PR's data.
5. No rollback complexity: reverting the PR removes the section; no data migration to undo since `title` is purely additive and optional.
